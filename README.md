## v2.20.83（2026-10-06）`check-version.mjs` 的 `test()` 計數器改走字元掃描器

前一正式版：v2.20.82（GPT 2026-10-05 已發布上線，Claude 當天完成二次複查並備存）。本版直接建在它之上，**沒有未發布的候選區間**。

使用者 2026-10-06 裁示「**我選乙**」＝修。這一件是 2026-10-05 **GPT 複查時抓到我說錯話**而浮上來的：
我在 v2.20.82 的交付說明裡寫「這一支**沒有**正規式計數守門；54 支測試檔兩種數法一致」，
**兩句都錯**——守門就在 `check-version.mjs` 第 501～505 行，而且是 **55** 支。

### 缺陷（體質問題）

`check-version.mjs` 原本用「正規式刪註解 ＋ 行首錨點」數 `test(`，兩個毛病：
① 正規式刪註解**會被字串裡的註解符號騙**。v2.20.82 時有 **4 支**測試檔的字面值裡含 `/*` 或 `*/`
（`manual-names.test.mjs` 兩處、`no-hardcoded-paths.test.mjs`、`plaintext-markup.test.mjs`、`wording.test.mjs`），
它們是在測「專案自己的註解／標記規範」，所以那個符號是**刻意且長期**存在的。
以 `manual-names.test.mjs` 第 205～206 行為例，正規式把第 205 行字串裡的 `/*` 與第 206 行字串裡的 `*/`
配成一對，**吞掉 2 行、54 個字元的真實程式碼**。
② 行首錨點數不到 `});test(` 寫在同一行的。

⚠️ 姊妹系統路口轉向 2026-10-05 已經真的被 ① 騙過（`v170-features` 被數成 13，實際 14）。

### ★ 真實檔案上的反證（不是假設）

本版新增的守門檔 `test-call-count.test.mjs` 自己的 fixture 裡就有 `"/*"` 字串：
**新計數器數出 8 條，舊計數器只數到 3 條——差 5 條。**
也就是說，只加守門卻不換計數器的話，日後只要有文件宣稱它的條數，
那條守門就會**逼文件去寫 3**。規則檔自己寫著「守門逼著文件去寫一句假話，比沒有守門更糟」。

### 改了什麼

- **新增 `test-call-count.mjs`**：認字串／樣板字串／正規式字面／兩種註解的**字元掃描器**。
  **沒有新增任何依賴**（本專案只有 3 個開發依賴、沒有 typescript，所以刻意不照抄另兩支的語法樹做法）。
  另外刻意匯出 `legacyRegexCount`（舊寫法）**只給守門當反證基準用**。
- **`check-version.mjs`**：那 5 行換成 `countTestCalls(…)`；`LAST_RELEASED` 81 → 82。
- **新增 `test-call-count.test.mjs`（8 項）**：第 1 條**把舊寫法本身當成比較基準**，
  所以只要有人把計數器改回正規式版就會紅——**這支守門在結構上不可能變成恆綠**。
  （刻意避開路口轉向 2026-10-05 踩到的坑：那一支的第一條反證因為 fixture 擺法，
  舊寫法也剛好數對，換回舊版並不會紅，是 GPT 抓到的。）

**判準**：只數「行首／`;`／`{`／`}` 之後」的 `test(`。刻意與舊寫法等價再加上 `});test(` 那一種，
GPT 校正：當時原有55份測試檔條數不變，但新增那份正是新8／舊3；不能稱56份全部同數。

**交通計算、Parser、匯入、混批、日期、覆蓋主鍵、IndexedDB、備份還原、樣式、Excel、趨勢、結論
全部未動；依賴未新增／未升級／未移除。**

### 我自己在量測上犯的錯，照實記

⚠️ 2026-10-05 我報過「那個字串會讓正規式吞掉 **36 行／1,079 字元**」——**那個數字是錯的**。
我的量測腳本去找單引號的 `'/*'`（檔案裡其實是雙引號），`indexOf` 回傳 −1，
於是它從 −1 開始找，**量到的是檔案自己的檔頭註解**。正確是 **2 行／54 字元**（已逐行肉眼核對）。
我後來又寫了一支「比對吃掉範圍 vs 真正註解範圍」的腳本，它報 9 支檔案、最大 23 行視窗
——**那支也是錯的**（把一個完全正常的單行註解判成誤吃）。所以一律改用**守門自己那支掃描器**去數。
➡️ 教訓：**量測工具本身也要有反證**。

## v2.7 更新

### 修正：匯出的 Excel 圖表會讓 Excel 要求「修復」，修復後圖表全部消失

- 「LOS 圖表」頁下載的可編輯圖表檔（旅行速率趨勢圖、LOS 趨勢圖），內部的圖表 XML 有四處欄位順序不符合 ECMA-376（Excel 的檔案規格）：
  1. 數值軸把 `<c:majorGridlines>`（格線）排在 `<c:numFmt>` 之後，規格要求它必須排在 `<c:axPos>` 之後、`<c:title>` 之前。
  2. LOS 圖把 `<c:majorUnit>`（刻度單位）插在 `<c:majorGridlines>` 前面，規格要求它排在 `<c:crossBetween>` 之後，結果整個數值軸的順序連鎖出錯。
  3. LOS 圖的座標軸範圍寫成 `<c:min>` 在前、`<c:max>` 在後，規格要求 max 在前。
  4. LOS 圖由折線圖改成長條圖時，`<c:gapWidth>` 被接在結尾（`<c:axId>` 之後），規格要求它排在 `<c:axId>` 之前。
- Excel 開檔時會逐一驗證這些 part，任一處不合規就判定檔案毀損、跳出「我們發現…部分內容有問題。您要我們盡可能嘗試復原嗎？」；按「是」之後 Excel 會直接丟掉整張圖表，因此使用者看到的是「只有數字、沒有圖」。LibreOffice 較寬鬆，能開起來不代表 Excel 能開。
- 四處全部修正，並新增自動檢查（`ooxml-check.mjs`），往後每次改版都會驗證匯出檔的結構、`[Content_Types].xml` 覆蓋率與 relationship 對應是否完整。修正後圖表可直接開啟並保持可編輯。

### 修正（全面檢查）

**Excel 讀取**

- 標題含有數字時會被誤讀成數值。例如「方向1平均總旅行速率：」會讀成 1、「平均總旅行速率（07:30~08:30）」會讀成 7，整份資料的服務水準全部變成 F 卻毫無警告。現在只有「冒號後面緊接著數字」才視為標題自帶數值。
- 行駛速率可能抓到隔壁方向的值。距離相同時改為優先取下方的標籤。
- 延滯只在「該方向自己的區塊」內尋找，不再抓到上一個方向的延滯表而讓兩個方向拿到相同數字。
- 總延滯缺少其中一項時，改為判定讀取失敗，不再把缺的那一項當成 0（舊版會嚴重低估總延滯卻照樣通過檢核）。
- 一張工作表若不是剛好兩個方向區塊（例如另有一個雙向平均區塊），改為明確報錯，不再用位置猜測而漏掉真正最差的方向。

**資料安全**

- 載入格式不對的備份檔時，原有資料不再被破壞。舊版會邊解析邊改資料，出錯後只顯示「這不是有效的備份檔」，實際上原本的計畫已被覆蓋且無法復原。
- 預覽之後若改了民國年或季度，預覽會自動失效並提醒重新預覽，不會再發生「寫進舊季度、紀錄卻寫新季度」。
- 同一批次內若有兩份檔案被判定為同一路段＋日別（會互相覆蓋），會列出檔名並擋下。
- 切換計畫、刪除計畫或清除全部資料時，未寫入的預覽會一併清空，不會寫到別的計畫。
- 民國年限定為 90～200 的整數，打錯不會再產生清不掉的幽靈季度。
- 計畫編號不得包含「|」符號（會導致刪除計畫時波及其他計畫的設定）。
- 匯入紀錄的復原新增保護：資料已被改名、合併或重新匯入時會擋下並提示改用備份還原，不會再把改名前的舊路段整批復活。
- 存檔失敗（無痕模式、儲存空間不足）會明確提示，不再靜默失敗。
- 匯入的專案包內容一律逸出後才顯示，避免夾帶指令碼。

**計算與設定**

- 刪除速限版本後，受影響的季度會正確退回基本速限並重算，不再停留在已刪除版本的速限。
- 路段改名或合併時，速限版本（有效期間、查證來源與人員）會一併搬移，不再變成孤兒而讓速限悄悄退回預設值。
- 速率缺值時速限比不再被算成 0（會被誤判為 F 並成為代表紀錄）。
- 自訂的服務水準門檻若剛好等於舊版預設值，不再於每次載入時被清掉。
- 期間排序一律依實際先後，民國 99 年與 100 年的資料不會再排反。
- 明細 CSV 的欄位改取所有列的聯集，不會因為第一列是舊版資料而漏掉來源欄位。
- 報告文字草稿不再被其他操作自動覆蓋；成果範圍也不會跨計畫沿用。

以上修正不改變既有的服務水準門檻、代表紀錄選取規則與總延滯計算方式。

## 發布步驟

以下保留首次建立網站的說明。**本 Repository 已存在**，維護更新一律沿用 `BaoToast/Travel-speed` 的 `main` 與既有 Pages 根目錄設定，不重新建立 Repository、不搬遷正式工作区、不另加部署 workflow。實際發布門檻以 `PROJECT_HANDOFF.md` 第 14～15 節為準。

1. 在 GitHub 建立新的儲存庫。
2. 將本資料夾內全部檔案上傳到儲存庫根目錄，包含 `.nojekyll`。
3. 進入儲存庫的 `Settings` → `Pages`。
4. 在 `Build and deployment` 選擇 `Deploy from a branch`。
5. Branch 選擇 `main`，資料夾選擇 `/ (root)`，再按 `Save`。
6. 等待 GitHub 完成發布後，按 `Visit site` 開啟正式網址。
